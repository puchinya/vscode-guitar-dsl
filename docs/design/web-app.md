# GuitarDSL Web application design

- Status: Current

## Context and goals

Issue #166 adds a static Web SPA alongside the existing VS Code extension. The Web app shares GuitarDSL processing, score UI, document contracts, and PDF rendering where their behavior is host-independent. Each application remains independently buildable and releasable. The extension keeps its existing VS Code `TextEditor`, commands, activation, Webviews, and VSIX boundary.

The design follows the approved Issue #172, #174, and #180 contracts. It does not add a backend, authentication server, SSR, separate score model, new syntax, or full-Drive scope. The public behavior is owned by the [Web application specification](../specs/web-app.md).

## Architecture

### Product and workspace boundaries

- The repository contains the existing VS Code extension at the root, the browser application in `web/`, and shared workspaces in `packages/{core,ui,document,pdf}/`.
- The root package continues to expose `main: ./out/extension.js`. The extension and Web app have separate build configurations and release artifacts. The Web app is built as static assets with Vite 8, Vue 3, TypeScript, `@vitejs/plugin-vue`, and `vue-tsc`; it uses Single File Components and the Composition API. Vue is confined to `web/`: no Vue code enters shared packages or the VS Code extension. CodeMirror 6 remains a Web-only editing component and does not replace the VS Code TextEditor. Pinia is confined to the Web app and serves only as a display projection of Controller snapshots. `.vscodeignore` excludes Pinia and its package-only dependencies from the VSIX. Router and SSR are not introduced.
- Workspace packages expose explicit build outputs and package exports. VS Code packaging bundles the shared runtime into the extension; a VSIX MUST NOT rely on workspace symlinks being available at runtime. `.vscodeignore` excludes Web source, built SPA distribution, and shared package source/tests from the VSIX.
- Existing host-independent logic moves to `packages/core/` instead of being copied. Temporary root `src/` re-export shims are allowed for compatibility during migration, but logic has one owner.

### Shared package responsibilities

| Package | Owns | Must not own |
|---|---|---|
| `packages/core` | Compiler, parsed score, score transforms, SVG/layout, play order, timeline, shared progression source planner, host-independent Capo/Beginner/Transpose section models and validation | VS Code APIs, browser DOM, storage, OAuth, filesystem APIs, a second AST or timing model |
| `packages/ui` | Host-independent Preview, Inspector, chord and variable editors, shared settings renderer and progression markup, styles, playback and practice controls | File persistence, application storage, `acquireVsCodeApi`, OAuth, direct host file I/O |
| `packages/document` | Document identity, revision, session identity, source-preserving change sets, save requests and change event contracts | Host-specific `TextDocument`, IndexedDB or Drive API calls |
| `packages/pdf` | `renderPdfBytes(dsl, options, fontBytes): Promise<Uint8Array>` and shared page selection/render contract | Node `fs`, `path`, or `Buffer` in common code; separate score-page SVG rendering |

Each app supplies adapters for its host boundary. The VS Code extension adapts `TextDocument` and `WorkspaceEdit`, Webview messaging, Node PDF save dialogs, CSP, and theme values. The Web app adapts the mutable browser buffer, DOM events, IndexedDB, Google Drive, browser fonts, Blob downloads, and browser theme/locale preferences.

The shared settings sections consume a plain source snapshot and return display models; host adapters own source identity/revision checks, messages, confirmation, and the single undoable apply. The Web and VS Code Inspector use the same settings renderer from `packages/ui/src/inspectorSettings.js` and the same progression-panel markup from `packages/ui/src/progressionInspectorMarkup.ts`. Progression candidates are applied through the source-preserving planner in `packages/core/src/progressionSourceEdits.ts`. The UI build synchronizes the canonical settings script to `media/inspectorSettings.js` for the VS Code Webview.

### Web application composition

- `web/src/main.ts` imports the shared styles, creates one `WebWorkspaceController`, one Pinia instance, and the Web I18n instance from the Controller's initial snapshot locale, attaches the single workspace store before mounting `App.vue`, installs Pinia and I18n, mounts the Vue hosts, and starts the controller after those hosts exist. The runtime registers production PWA support. `main.ts` contains no application state, DOM renderer, event router, or storage logic.
- `web/src/controllers/workspaceController.ts` exposes the only Vue-facing `WebWorkspaceController` service and owns its startup/disposal lifecycle. It lazily loads `web/src/workspaceRuntime.ts` after Vue has mounted the leaf hosts; that private implementation is the sole owner of `AppState`, `OpenTab`, editable source/revision, document identity, tab selection, draft and Drive save queues, Drive account/generation, appData sync, and exclusive Inspector/Preview audio lease transitions. The service exposes the fixed `snapshot()`, `subscribe()`, `dispatch()`, `prepareForReload()`, and `dispose()` API. Commands are discriminated unions; async work captures full document identity, expected revision, and session generation and revalidates them before applying a result.
- `web/src/stores/workspaceStore.ts` is the only Pinia store (`workspace`). Its `view` is a `shallowRef<Readonly<WorkspaceViewSnapshot> | null>` that replaces the snapshot reference received from the Controller; it does not clone or deep-reactify snapshot contents. Its `problemSummary` is a pure display computed. `attach()` accepts only `snapshot()` and `subscribe()`, keeps at most one subscription, treats repeated attachment to the same Controller as a no-op, rejects a different Controller until detach, and invalidates callbacks from a detached subscription. `detach()` is idempotent, does not dispose the Controller, and retains the last view until teardown. Store state is not an edit path: application code does not assign `view`, call `$patch()`/`$reset()`, or write source, revision, Drive, or persistence state through Pinia. `EditorView`, `AudioContext`, `GoogleDriveApi`, and `OpenTab` are never made reactive.
- State transitions follow Controller mutation → snapshot emission → store view reference replacement → Vue render. Vue watchers and effects do not initiate source edits, saves, or Drive synchronization. The store begins with `view === null`; the synchronous attach in `main.ts` supplies the initial `ready: false` snapshot before the first Vue render.
- `workspaceRuntime.ts::state.locale` and its existing IndexedDB preference remain the only locale owners. `createWebI18n()` statically imports the English and Japanese Vue-owned UI message bundles with Composition API (`legacy: false`) and English fallback. `App.vue` watches the Pinia snapshot's locale and projects it one way into the global Composer and `document.documentElement.lang`; the watcher adds no Controller subscription, persistence, or command path. SFCs use `useI18n({ useScope: 'global' })` for their fixed text, tooltips, and ARIA labels. Controller-generated menu snapshots, Help and Inspector DOM, and shared package translations retain their existing owners and APIs. Static imports keep both locales in the offline PWA bundle.
- `web/src/App.vue` and the workspace SFCs own the shell, Explorer, tabs, menus, Problems, and panels. They render read-only snapshots and dispatch typed commands; Vue and legacy imperative renderers never own the same DOM subtree.
- `App.vue`, `HeaderBar.vue`, and `ProblemsPane.vue` consume the workspace store. `HeaderBar` and `ProblemsPane` no longer receive snapshot props; `WorkspaceShell` and its other child views keep their existing snapshot props for this staged migration. Commands from every view still pass through the existing typed event path to `controller.dispatch()`. The app detaches the store before disposing the Controller on non-persisted page exit or Vue unmount. Persisted BFCache `pagehide`/`pageshow` keeps the same subscription, store, Controller, and editor alive while forwarding the existing lifecycle commands. Repeated teardown is harmless, and hot reload cannot add a second subscription to the same Controller.
- `web/src/editor/sourceEditor.ts` owns the CodeMirror 6 surface hosted once by `SourceEditorHost.vue`. The controller remains the sole source/revision authority; each open tab retains its CodeMirror `EditorState` (including selection and history) and scroll position. Tab changes call `setDocument(key, source)` on the existing `SourceEditorSurface`; Vue `v-model` never duplicates the source. View and splitter changes do not recreate the `EditorView` or tab state.
- CodeMirror's rendered document uses LF line breaks for editing. The adapter maps transactions back through the existing `preserveLineEndings` rules so untouched CRLF and CR spans remain unchanged. IME composition is not flushed, completed, or replaced before the browser commits it.
- Human input, search/replace, deterministic completion, and a planner-produced Preview or Inspector change set each apply as one CodeMirror transaction and one undo step. Only committed human edits advance the source revision, write an IndexedDB draft, and trigger derived-state recomputation. View-mode changes do not create source transactions.
- Syntax highlighting is built from source ranges produced by the existing tokenizer and attached as CodeMirror decorations. It does not generate HTML and does not add another GuitarDSL parser. Completion uses local metadata fields, line prefixes, variable references, and syntactically safe constructs; it makes no model or network call.
- CodeMirror lint maps only the shared `ParsedScore.diagnostics` values to editor ranges. The Problems tool window presents that same ordered diagnostic collection. It does not parse or validate DSL independently.
- `WorkspaceShell.vue` owns CSS Grid presentation for Source/Split/Score and mounts `GridSplitter.vue` for the Explorer, Source/Score, Inspector, and Problems boundaries. `GridSplitter.vue` shares pointer capture, pointer lifecycle, double-click reset, orientation-appropriate keyboard input, and separator accessibility attributes, then emits a typed splitter command. `workspaceRuntime.ts` retains each boundary's size calculation, clamping, reset value, and persistence. The Source/Score flex basis consumes the snapshot's `--split-ratio`, so pointer and keyboard updates resize the rendered panes. Hover and focus feedback is shared by all four splitters in Light and Dark themes. The controller persists the existing `web-layout-v1` record with panel state, dimensions, center ratio, and view mode. Width-driven collapse stays transient.
- Workspace control state comes from the Controller snapshot: Explorer and Inspector use their saved `aria-pressed` values, and Problems uses `aria-expanded`. CSS shows an active surface for each open control. Explorer's active icon and selected file row use a background surface without an inset left stripe. The Problems badge is conditionally hidden when the total diagnostics count is zero; closing Problems hides its splitter and collapses the splitter grid track with the panel.
- Dark theme menu hover and keyboard focus keep labels and shortcut text readable against the selected surface. `MenuLayer.vue` owns keyboard focus movement and the shared settings/context menu markup; theme-specific colors remain in the shell stylesheet.
- An effective viewport fallback collapses Inspector before Explorer and keeps the main grid overflow-free. User-controlled open/close state remains separate from this computed collapse. Four separators own Explorer width, center split, Inspector width, and Problems height; pointer capture, double-click reset, keyboard moves, and pointer cancellation are scoped to one separator.
- `DocumentTabs.vue` renders its tab list and view-mode controls only while at least one document is open; the empty row is an unlabelled, background-only surface with no bottom border. `WorkspaceShell.vue` keeps the stable Source and Score editor hosts mounted but applies `display: none` to `.split-view` while no tabs are open. This hides both panes, their empty states, and their descendants from the rendered view and accessibility tree while preserving host ownership for reopening. Opening a document reveals the panes in the existing selected mode and layout. The dark-theme separator before view controls uses the shell's `#424652` boundary color.
- `InspectorHost.vue` uses the global Vue I18n Composer for its visible pane heading, accessible pane name, and options label. The parked shared settings renderer still receives the Controller snapshot locale through its existing message API.
- New-score creation prompts for a base filename without an extension, strips a supported suffix if entered, and appends the fixed `.guitardsl` extension before storage and fallback document creation.
- The workspace host owns menus for Explorer roots/files, tabs, Problems, Preview, and the line-number gutter. A local file menu provides Open, Rename, Duplicate, Download, Download as PDF, conditional Move to Google Drive, and Delete. Rename presents only the base filename and appends the original supported extension after input, so the extension cannot change; extensionless names remain extensionless. Local duplication assigns the smallest unused positive suffix inside the IndexedDB documents write transaction so concurrent duplicate actions cannot claim the same local name; comparisons use Unicode NFC and case-insensitive matching. Downloads resolve the clicked file's current saved or draft source rather than the active tab. Local deletion confirms before removing a document; Drive root actions stay scoped to the active account/folder. The source text surface keeps the browser's native editing context menu. Preview includes parser-owned source bindings only while Edit mode is active; the source-position context action is disabled in Normal and Practice modes. A menu captures document identity/revision and Drive account; Preview messages also carry the clicked binding ID and render identity, all of which the host revalidates when an action runs. An invalidated target is discarded without applying an action.
- Edit-menu Cut and Paste retain a snapshot of the active tab, full identity, revision, selection, source, and composition status while awaiting Clipboard API promises. The editor checks that snapshot and its own CodeMirror state before dispatching a transaction. A changed target or active composition produces no edit; successful Cut/Paste uses one undo transaction.
- Tab close handlers operate on the tab object and re-read its index immediately before removal after asynchronous draft writes. Repeated close requests for the same tab are coalesced. Document opening rechecks identity after IndexedDB work and before insertion so concurrent opens resolve to one tab.
- `HeaderBar.vue` and `MenuLayer.vue` provide local bilingual Help, theme/language Settings, layout reset, Save/PDF, the Google Drive connection/account menu, and File/Edit/View menus. The header has no separate Account trigger/menu; the Drive menu shows the connected identity and Disconnect, or the relevant Connect/Reconnect action when signed out. Help/Settings remain independent of Preview's normal/edit/practice state. Escape and close restore focus to the invoking header button.
- `web/src/adapters/` translates browser events and host capabilities into the shared UI and document contracts. Shared UI does not import storage adapters. Leaf hosts mount and dispose the shared imperative Inspector renderer exactly once.
- `web/src/storage/` contains the IndexedDB adapter, Drive API adapter, appData state adapter, and transfer coordinator. `web/src/auth/` wraps user-initiated Google Identity Services token requests. Drive app state is owned by appData; local documents, drafts, and per-device layout remain in IndexedDB.
- `web/src/pdfExporter.ts` selects browser font bytes, calls the shared PDF byte API, then starts a Blob download. It does not call Node APIs.

### PWA assets and safe update lifecycle

- Vite uses `base: '/'` and `vite-plugin-pwa` 2.x with Workbox `generateSW` and `registerType: 'prompt'`. The manifest uses root `id`, `start_url`, and `scope`, `display: 'standalone'`, GuitarDSL names/colors, and generated 192 px, 512 px, maskable 512 px, and Apple touch icons derived from the existing sidebar SVG. Development-server runs do not register a service worker.
- The generated service worker precaches only same-origin production build output, including HTML, eager and lazy JavaScript/CSS, SVG assets, PWA icons, and the PDF font files. `navigateFallback` targets `/index.html`, `maximumFileSizeToCacheInBytes` is 8 MiB, `runtimeCaching` is empty, and `skipWaiting` / `clientsClaim` are false. Precache size and included assets are recorded during release verification.
- The service worker never intercepts Google Identity Services, Google Picker, OAuth, Drive/API, or other external requests. It does not cache authorization data, GuitarDSL source, IndexedDB content, PDF Blobs, or API responses. Local document durability stays exclusively in IndexedDB; an offline Drive draft remains local and visibly unsynchronized.
- A waiting worker is exposed through `PwaUpdatePrompt.vue` as explicit **Update** and **Later** choices. No automatic activation or forced reload occurs. On **Update**, the controller synchronously acquires an exclusive preparation gate before its first `await`, makes the application inert, and rejects new commands. It captures each open document's identity/source/revision, flushes completed editor transactions and pending local drafts, then drains pending appData work. After each await and again immediately before `SKIP_WAITING`, it verifies the captured document state, no active IME/editor publication, completed IndexedDB draft writes, and idle Drive/appData operations and queues. A failed check leaves the worker waiting, releases the gate, and restores interaction. The gate remains held through activation/reload; activation failure also releases it. Preview and Inspector audio stop before activation. The prompt explains that CodeMirror undo history may not survive reload.
- If the appData conflict dialog offers **Reload remote** during update preparation, that choice cancels the current update attempt. The runtime keeps interaction locked while it restores the remote folder and Drive tabs, then clears the account-keyed pending record only after restoration succeeds. A restore failure keeps the pending record and local drafts, reports an error, and leaves the worker waiting. After a successful restore, the gate releases and the user must choose **Update** again so a fresh workspace baseline is checked before activation. AppData writes are suppressed during this restore.
- `applyWorkspaceCommand` is the common tracked entry for workspace actions: it increments the in-flight count before invoking a handler, records its returned promise through settlement, and rejects new entries synchronously while update preparation or BFCache suspension is active. Update preparation locks first and fails closed if an accepted workspace action is still in flight; it releases the gate immediately, lets that action settle against the current workspace, and only takes the source/revision baseline on a later safe retry. Explicit Save is tracked from before its local draft write through the remote outcome, so selecting Update cannot discard it just because its Drive phase has not started yet. A failed Save keeps its IndexedDB draft and reports the incomplete remote result. Async clipboard handlers recheck the operation and update-attempt generations plus both lifecycle locks immediately after the browser clipboard promise and before `EditorView.dispatch`. Explorer refresh rechecks after the IndexedDB list before issuing Drive I/O and again before applying rows. Remaining async workspace handlers revalidate the captured lifecycle generation after each await that precedes a source/workspace mutation or a new request. Direct shared Inspector settings callbacks enter the same controller guard.
- BFCache suspension advances the workspace operation generation before marking the page suspended. Pending clipboard, tab/document, local-file, Drive, and Inspector-settings continuations compare their captured generation and stop before changing source/workspace state or issuing another request. Resume advances the generation again and revalidates the active identity/revision; it does not revive a stale continuation.
- A Drive document save captures its account ID, `GoogleDriveApi` instance, Drive generation, workspace generation, tab, and file ID. Each request and the later IndexedDB commit checks that ownership. If a write response arrives after the session ends, its result stays unconfirmed: it does not start a readback with a replacement token or commit the old session's result locally.
- Drive Explorer refresh has a monotonically increasing request sequence in addition to account/Drive/generation/folder checks. Only the latest request for the current online session may apply rows or authentication/error state, so an older success or 401 cannot overwrite a newer result. A stale request also cannot begin a Drive list after waiting on IndexedDB if the page went offline or the session/folder changed.
- `document.open-drive` validates the command's captured account ID and current row/session ownership before dispatching the open. This prevents an A-originated command from resolving a same-file-ID row belonging to B after an account switch.
- Workspace snapshots read parsed scores and diagnostic offsets from a document-derived cache keyed by identity, source/revision, locale, and parser options. The line-start table is computed once for that source and reused for diagnostics; cursor and selection notifications reuse parsed state. A new source/revision or parser option invalidates that entry.
- `PwaUpdatePrompt.vue` is a named, polite live region (`role="region"`, `aria-live="polite"`), not a modal dialog. It leaves editor focus and normal tab order available while Update/Later controls remain reachable.
- `App.vue` distinguishes a BFCache transition from page exit. For `pagehide.persisted === true`, a typed lifecycle command keeps the controller, EditorView, DOM ownership, and listeners alive, marks the workspace temporarily inert, and stops both Preview playback (through its existing audio lease protocol) and Inspector audition. `pageshow.persisted === true` reuses the same runtime, revalidates the active document/revision, refreshes workspace layout/snapshot, and restores interaction without replaying audio. A non-persisted `pagehide` or component unmount disposes once. `pagehide` starts no local persistence or network write.
- Reload, pagehide, and worker cache cleanup never delete IndexedDB. The service worker is origin-scoped, so development and production hostnames maintain separate registrations and caches. A macOS Dock installation and Safari tab may have separate site data; the app does not promise automatic migration or synchronization between them.

### Host-independent data flow

1. A host adapter resolves a stable document identity and its mutable source buffer.
2. An edit changes the buffer once and advances its revision. A derived source snapshot is sent to the shared compiler and render pipeline.
3. The core produces a `ParsedScore`, diagnostics, and SVG pages. The shared UI consumes these derived values; the editor buffer remains authoritative.
4. Preview and Inspector planners create source-preserving change sets against `{documentId, expectedRevision}`. The host validates both values at apply time. A stale or invalid change is rejected with zero source edits, after which derived UI is rebuilt from the current buffer.
5. Playback order and timeline are resolved through the shared core functions. `packages/ui` owns the `ProgressionAudioLeaseCoordinator`; the VS Code and Web host adapters provide Preview locking and Inspector playback ports. Preview/practice and Inspector audition use this exclusive lease, and lifecycle disposal releases playback and listeners.
6. PDF export uses the same page SVG renderer. The host-specific layer only supplies font bytes, chooses page options, and delivers the resulting bytes.

### Document and storage ownership

- `packages/document` defines identities as `{storage, fileId}` and contracts for source revisions, session identity, save requests, and change sets.
- An open document has one mutable source buffer. A compiler or Preview snapshot is derived state and cannot independently become the saved source.
- CodeMirror stores tab-local undo history and view state, while `OpenTab.source` and the host's source-preserving transaction remain the authoritative document. Before a synchronous redraw or document switch, the host flushes any completed pending CodeMirror transaction using the editor's captured document key. A stale external change set is rejected by the same identity/revision check before it reaches CodeMirror or the document buffer.
- Before a save or PDF snapshot, the host synchronously flushes the active editor into its owning `OpenTab`; if IME composition is active, the action stops and asks the user to finish composing. The `beforeunload` guard reads pending editor publication/composition state synchronously alongside per-tab persistence state, without starting asynchronous writes.
- The browser session stores open-tab identity and recoverable drafts in IndexedDB. Draft persistence and user-visible saved state are updated only after IndexedDB confirms the write.
- Layout preferences use a separate IndexedDB key so resizing or changing display mode cannot advance a source revision, alter Drive metadata, or mark a document saved. Preference writes are debounced; invalid fields fall back to the corresponding default.
- Local documents and Drive documents remain separate identities even when names match. Explorer renders both independently collapsible storage roots and their own lists at the same time; selecting a root does not hide the other tree or change open-tab identity.
- The Drive adapter keeps account-scoped metadata and open-tab sessions separate and uses only explicitly authorized files. Switching or disconnecting accounts retains each account's open tabs and drafts; Drive writes are enabled only when the connected account owns the active Drive tab. OAuth access tokens remain in memory. The selected folder ID is configuration, not a credential.
- Opening a restored document compares its current source and revision with the last committed record. A recovered draft is shown as a local draft until a successful local or Drive commit advances that saved baseline.
- A normal Drive save updates the existing `fileId` with media PATCH. `GoogleDriveApi.getFile` reads metadata, media, then metadata again under one captured token; a mismatch is an unconfirmed read and cannot be used to authorize a write. The adapter compares the stable source with the submitted source and the last confirmed baseline. Submitted-source equality completes with no PATCH; baseline equality revalidates the latest metadata and proceeds with one PATCH; any third source is a true conflict and returns before writing. The update targets the same fileId, verifies the live canonical library root and the score's parent chain immediately before PATCH, and confirms that the file is not trashed. It returns fresh name/parent/version metadata so a rename or move is not reverted locally. Saves are serialized by `{accountId, fileId}` in this app instance. After PATCH, the host reads the source back before committing the remote baseline. A network-unknown PATCH is reconciled with one readback; an unresolved result or HTTP 401/403/429/5xx keeps the draft and is never automatically resent.
- Reopening a score with both a saved Drive baseline and a local draft reads a stable remote source and compares it with both local versions. A remote match with the draft confirms and commits that draft; a match with the saved baseline refreshes metadata and preserves the draft; a third source opens the existing conflict choices. A new draft without a saved baseline is also compared with the stable remote source before it can be committed.
- ETag may be absent. When available, `If-Match` uses only the ETag from the same stable read as the content comparison; it is a best-effort guard, not the concurrency guarantee. GET→PATCH remains non-atomic, and another device's write in that interval may be overwritten. This residual race is accepted by the Issue #166 Architecture Decision Addendum (`6860479905`) and is disclosed in the Drive UI and Help.

### Drive appData state protocol

The `drive.file` scope continues to cover score files opened through Picker or created by GuitarDSL. The additional `drive.appdata` scope is isolated to one hidden `guitardsl-state-v1.json` per account. `DriveAppDataStore` owns discovery, validation, and updates; it never stores source text or credentials. Its exact schema is `{schemaVersion:1, selectedFolderId:string|null, folderPrompt:'unasked'|'deferred'|'completed', openDriveFileIds:string[], activeDriveFileId:string|null, recentDriveFileIds:string[]}`. Open and recent arrays are deduplicated and capped at 30 and 50.

Discovery paginates `files.list` with `spaces=appDataFolder`, `trashed=false`, an exact state-file name query, and a MIME check. Existing candidates are sorted by oldest `createdTime`, then lexical ID; duplicates cause a warning and are retained. A missing file is created once under appDataFolder. An uncertain create result gets one re-list/read; the client never blindly repeats POST. Subsequent updates target that same file ID through media PATCH and are accepted only after readback matches the submitted JSON.

Before comparing, the adapter reads metadata, the validated state, then metadata again; a read spanning versions is unknown and cannot authorize a PATCH. On version mismatch, latest content equal to the desired state is saved with PATCH0; content equal to the loaded baseline is rebased onto the latest version and updated once after revalidation; a third state is a true conflict that offers remote reload or explicit local preference. Choosing local preference uses the latest stable baseline for one PATCH. An uncertain PATCH gets one readback only; a differing readback remains unknown with pending state and is never automatically resent or reported as a confirmed content conflict. Malformed JSON, unknown versions, permission failures, offline state, and unknown outcomes never trigger replacement-file creation.

The sync controller captures account ID, Drive instance, Drive generation, workspace lifecycle generation, and a monotonic desired-state sequence at every operation boundary. The latest desired state is written to the account-keyed pending record before remote PATCH; old timers and queued snapshots cannot overwrite or clear it. A completion from an older sequence may refresh the known remote baseline but cannot show the newest state as saved. If a PATCH may have reached Drive after its session ended, the outcome remains unknown; the next eligible sync first loads remote state. A mismatch with the latest desired state opens the existing local/remote choice, and only an explicit local choice authorizes one PATCH against the exact snapshot shown. Repeated scheduling of the same state does not start a timer or PATCH, and Local-only work with unchanged appData sends no PATCH. The controller loads current remote state before Drive-tab restoration and does not import obsolete `drive-folder:<accountId>` or `workspace-drive:<accountId>` IndexedDB settings. Pending records use the strict existing schema and contain only appData references and sync metadata, never source, drafts, local document IDs, credentials, or email. On reconnect, an unrelated pending state and remote state still require a user choice. Remote choice validates the folder, restores matching Explorer and Drive tab state, preserves local drafts, and clears pending only after the selected state is applied. A remote state with no selected folder, no open or active Drive references, and an `unasked` or `deferred` prompt is a valid unset-library state when no root exists; restore applies an empty Drive session without creating a root or updating appData. If the state is `unasked`, its setup prompt runs only after the restore releases the sync queue and interaction lock, and **Later** leaves remote appData unchanged. Missing or mismatched selected roots and Drive tab references without a verified root fail closed and retain pending state. Remote restore never waits for work enqueued on its own appData queue. Local choice updates from the loaded remote baseline; a pending record clears only after matching readback. Errors and offline state retain the record, `beforeunload` warns, and `pagehide` starts no network write. Folder, open-tab, active-tab, and recent-list changes debounce for roughly one second and serialize per account.

During connection, folder validation updates the loaded account session instead of deriving Drive tab references from the workspace's temporary pre-restore tab list. AppData scheduling requested during connection is deferred until folder setup and Drive-tab restoration finish, then recomputes the current state. A local-session persistence continuation also captures the account, Drive instance, and generation so a completion from an earlier connection cannot schedule sync for the new one.

### Google Drive library protocol

The GoogleDriveApi adapter owns Drive REST request encoding and normalized metadata; it does not own workspace state or UI decisions. workspaceRuntime.ts, behind the WebWorkspaceController, is the single owner for account/session generation, library roots, per-folder load state, import and mutation continuations, saved tabs, and pending recovery records. Pinia remains a read-only snapshot projection. Explorer rows and context menus dispatch typed commands and never call the Drive adapter directly.

The library root is a real top-level My Drive folder named GuitarDSL. On connection, the runtime discovers an accessible folder with that exact name and parent using a `files.list` query constrained by `'root' in parents`; it does not call `files.get('root')` or require the My Drive root's metadata to be readable. Drive may expose only app-authorized files under the `drive.file` scope, so root discovery must not depend on broader OAuth scopes or root metadata access. The list query establishes the direct-root relationship, while each returned candidate's `parents[]` retains its actual parent ID. If list discovery does not return it, the current appData selectedFolderId is checked as a candidate and reused only when the same ID is also returned by the canonical-root query and its own metadata confirms its name, folder MIME type, and untrashed state; arbitrary IDs are ignored. The runtime keeps that physical ID and sets appProperties guitardslLibraryRoot=1 when needed. It reads the candidate back by its own ID, verifies the marker, and confirms that ID remains in the canonical-root query before committing it to selectedFolderId. To create a root, omit `parents` so Drive places it in My Drive, then read the returned ID back and reconcile it against the same root-constrained list query. A lost create response gets one list reconciliation and never a second create. Folder discovery is constrained to app-accessible items and does not broaden OAuth scopes. The app does not migrate obsolete local folder settings and does not copy, move, or delete content from any other folder. If no eligible root exists, the user confirms creation of a new root or defers.

The tree is a projection of physical Drive parent relationships. The runtime loads a folder's direct children with paginated files.list requests constrained by parent ID and trashed=false. It filters supported score extensions and folder MIME type, detects repeated page tokens, verifies the captured account and generation before publishing results, and loads descendants only when their folder expands. Explicit refresh invalidates the affected cache. The app never recursively downloads the entire Drive tree or claims a complete listing: drive.file exposes only app-created and individually authorized items even when their parent folder is visible.

Each immutable snapshot row carries its Drive identity, item kind, parent ID, display name, account ID, generation, and relevant loading/access state. A context menu captures {accountId, driveGeneration, fileId, kind} when it opens. The command rechecks that context before any API call and before applying its result. An account switch or later generation makes the old command inert.

Picker is a file-import adapter, not a document-open or destination-picker path. It accepts multiple files, rejects folders, Google-native documents, unsupported extensions, and any source whose Picker or live Drive metadata MIME type is not `text/plain` or `application/octet-stream`; it copies each allowed source into the clicked library folder with files.copy. The original ID and contents are unchanged. The runtime handles same-name choices per item and verifies the returned new ID, parent, name, MIME type, and source content before reporting success. It reports partial outcomes individually. An uncertain copy is reconciled against the known operation and target; it is not blindly repeated. Operation IDs and returned IDs are retained in the account-keyed IndexedDB recovery record so reload or retry cannot create a duplicate. The record stores the UTF-8 SHA-256 digest of the source content, never the source text or credentials.

Before each folder creation, score creation, or copy, the runtime validates the canonical root and the clicked target folder with live metadata and the actual parent chain. `isLibraryFolder()` is only a cached UI guard. Picker selection is revalidated after Picker returns and again before every `files.copy`; a moved or trashed root/target prevents the write. The runtime checks the created/copy item's readback parent and identity before reporting success. The Drive REST API does not make validation and write atomic, so this reduces stale-target writes but cannot eliminate a concurrent move between the last validation and the API request.

Import and duplicate share the account-keyed copy-operation journal in the existing IndexedDB settings store. A record contains an operation ID, kind (`import` or `duplicate`), source ID, target folder ID, requested name, UTF-8 SHA-256 of the pre-copy source content, whether the copy request may have been sent, and a returned copy ID when known; it never stores source text or credentials. Legacy import records without a source digest are treated as potentially sent imports. They can be confirmed only by re-reading the original source and matching its current content digest to the copy; if the source or copy cannot be read or the digests differ, the record remains unresolved. Journal changes use one IndexedDB readwrite transaction so concurrent tabs cannot lose each other's records. The record is written before COPY, marked possibly sent before the request, and removed only after the copy's ID/marker, target, name, allowed MIME type, and source digest are confirmed. Reconciliation checks a known returned ID first, then searches all marker pages. An unresolved record blocks a same-operation repeat and is retained across reload and reconnect; a later explicit retry cannot issue a second COPY until reconciliation confirms the first result or the request is proven not to have been sent.

Folder creation and rename use the clicked parent and stable folder ID. Folder moves and trash are absent. Score rename is a metadata-only update that preserves the same ID, content, parent, and extension; duplicate uses Drive copy and a new ID; move is constrained to two folders beneath the same verified library root; trash is confirmed and never permanently deletes. Every operation validates item kind, parent, authorization and captured generation, then reads the result back before the UI reports success. A dirty score being trashed remains recoverable in its open tab and IndexedDB draft. The existing per-{accountId,fileId} save queue serializes Drive save, duplicate, and metadata mutations for the same score. After waiting in that queue, a move re-reads and verifies both source and destination folders are untrashed folders within the same library root before changing parents. Normal save remains a media PATCH to the existing ID followed by content readback.

“Open in Google Drive” builds a folder URL from the clicked folder ID. For a file it uses a verified HTTPS webViewLink on a trusted Drive host, or the file-ID URL fallback. The action uses window.open in the user gesture with noopener,noreferrer; if popup opening is blocked, the UI exposes the direct URL as a normal link. A null return is not by itself an error. The URL and target ID are bound to the menu snapshot, so the active tab cannot substitute for the clicked row. This operation has no workspace, document, undo, save, expansion, or appData side effects. The Google account active in the new browser tab may differ and may not have access.

### Google Drive transfer protocol

This protocol covers moving an open local document into the library. Moving an existing Drive score between two library folders is a separate metadata operation described in the Google Drive library protocol.

Local-to-Drive move is a recoverable sequence rather than a rename:

1. Persist the active local buffer and retain the local document identity.
2. Upload to the selected folder without silently overwriting a same-name file.
3. Record the returned Drive file ID and read the file back.
4. Verify the remote identity and content against the uploaded source.
5. Delete the local original only after successful verification.
6. Rebind the open tab to the Drive identity and refresh its revision/version metadata.

Failures before step 5 leave the local source intact. If upload succeeded but readback or local deletion failed, the transfer record retains the Drive file ID so retry reconnects to that same file rather than uploading a duplicate. If both copies remain, the UI reports that state. Account changes cannot reuse a transfer record belonging to another account.

### PDF boundary

The PDF package consumes the common score-page SVG output and returns bytes. Browser and Node builds may use host-specific bundling for `pdfkit`/`svg-to-pdfkit`, but they share page selection and SVG generation. Before replacing or forking the renderer, verify that the current PDF dependencies can be bundled in both environments. If that requirement conflicts with the current Node implementation, report the exact incompatibility rather than silently changing the PDF engine. Japanese font bytes cross the API as `Uint8Array`; common code does not depend on `Buffer`, `fs`, or `path`.

## Failure handling

- `closeTab` coalesces same-tab requests in an in-flight `WeakMap<OpenTab, Promise<void>>`. Each caller awaits the same operation through draft persistence, tab removal, and session persistence, so a remote restore cannot mistake an unfinished user close for a completed one.
- Google OAuth accepts a token only when both requested scopes are present in the GIS `TokenResponse.scope` and `hasGrantedAllScopes` accepts them when that helper is available. Partial consent clears auth state and presents an explicit reapproval error before `/about` or appData requests.
- When appData sync is pending or failed, disconnect waits for the account-keyed pending write to settle and asks for confirmation. Confirmed disconnect clears the in-memory auth/session binding while retaining the IndexedDB pending record and local drafts for account-specific reconciliation on reconnect.
- Compiler, renderer, planner, and PDF failures stay typed at their owning package boundary; they are not converted into successful empty output.
- IndexedDB errors do not clear the in-memory source. The UI reports unsaved state and enables file download.
- Each Drive open captures its account ID and `GoogleDriveApi` instance. A multi-request `getFile` read also pins its access token across metadata and media requests, so an account reconnect cannot switch credentials halfway through that read. Picker, Drive-read, conflict-dialog, and IndexedDB continuations recheck the captured session before starting writes and before changing tabs or Explorer state; a result from an ended session is discarded. Account-scoped keys always use the captured account ID.
- The editor compares each tab's current revision/source with its last successfully persisted draft and tracks queued writes. `beforeunload` requests the browser's native confirmation while a revision is pending or failed; it starts no asynchronous IndexedDB work. A persisted BFCache `pagehide` stops playback without destroying the editor/controller. Every persisted `pagehide`, including one received during draft reconciliation, advances the workspace generation and captures a fresh suspension baseline; repeated suspension does not repeat disposal or audio shutdown. On `pageshow`, interaction remains suspended while one IndexedDB read transaction obtains the latest saved-or-draft CAS baseline for each open tab. Only the latest `pageshow` reconciliation may unlock interaction, release the Preview audio lock, or start deferred Explorer/Drive/appData work. A baseline matching the in-memory source/revision is adopted, a baseline still matching the previous persisted value permits retrying the current draft, and any unrelated value or read failure preserves both copies and asks the user to review/export before saving again. Each queued draft write captures the workspace generation and rechecks it before starting IndexedDB work and before applying success or failure state, so an invalidated continuation cannot poison the resumed tab. A non-persisted page exit invalidates pending reconciliation and disposes playback/runtime resources once; neither pagehide path starts asynchronous writes.
- A stale change set or mismatched document ID is rejected before applying any source edit. One rejected operation cannot partially modify the document.
- Drive authentication, permission, rate-limit, network, and server failures retain local source and drafts. A PATCH 401 marks authorization expired and changes the Connect action to explicit Reconnect; after reauthentication the user checks Drive before retrying. A PATCH 403 remains a permission error and does not start an authentication loop. Neither status triggers an automatic PATCH resend.
- Library folder/file 403 and 404 responses are access or availability outcomes, not proof that an item was deleted. A failed import, rename, move, or trash retains source and draft state. Unknown create/copy/metadata-write results get one bounded reconciliation against the captured target and operation ID; no blind second POST/PATCH occurs, and the UI reports success only after readback.
- A stale Drive menu or continuation whose account, generation, item ID, kind, or parent changed performs no action. Open-in-Drive uses the captured target and never changes the active tab or document.
- AppData discovery and parsing failures retain the pending state and do not create a replacement file. Unknown schema versions, malformed JSON, duplicates, version conflicts, and uncertain writes are surfaced independently. One uncertain create/update is followed by at most one list/read reconciliation; no automatic POST/PATCH retry occurs.
- An observed Drive version conflict offers reload, save as a separate file, or cancel and sends no PATCH. A concurrent update after preflight is an accepted residual race; the UI and Help disclose that another device's nearly simultaneous write may be overwritten.
- A network failure or malformed PATCH response is followed by one Drive readback. If that readback matches the submitted source, the write is verified; otherwise the app keeps the draft, reports an unconfirmed outcome, and does not retry automatically. HTTP 401/403/429/5xx also keep the draft and never trigger an automatic write retry.
- Conflict reload and save-as capture the tab identity, source, and revision before their asynchronous Drive requests. Before applying a response, the host checks that the same tab still has that snapshot. A newer edit remains a local draft; reload asks the user to choose again, while a save-as upload opens the submitted snapshot separately and leaves the newer edit in its original tab.
- Transfer recovery is keyed by account and returned Drive file ID. Upload success is not enough to delete the local original; remote readback and validation are required.
- Preview and Inspector audio share an exclusive lease. The Inspector's fallback completion timer uses playback duration in seconds and playback speed, then stops the audio and releases the Preview lock at natural completion. On view disposal, document switch, or host shutdown, listeners and audio resources are released and outstanding operations cannot mutate a newer document revision.
- Untrusted DSL and metadata are rendered through escaped text and constructed SVG attributes. CSP and host-specific Webview security continue to be enforced by the respective adapters.
- Workspace mode changes and resize events update CSS grid tracks and the existing Preview viewport. They do not recreate the Preview iframe or reset its scroll, playback state, editor history, source revision, draft, audio lease, Drive identity, or audio resources.
- A Problems row opens its source document and reveals the exact compiler range from the shared diagnostic. Reopening or switching documents resolves the current tab identity before focus; a diagnostic cannot target a previous document merely because the file name matches.

## Alternatives considered

- **Separate repository or new backend:** rejected by the contract; the SPA and extension share core behavior in one repository and the Web product is static.
- **Vue 3 in the Web app:** accepted by Issue #174 to give the Web shell and panels explicit SFC ownership while retaining one imperative state-transition owner. Vue stays out of shared packages and the VS Code extension. **Pinia:** adopted by Issue #176 only as a Web-only, one-way display projection so the shell, header, and Problems view share the Controller's latest snapshot through a standard Vue store. The Controller remains the sole state-transition and side-effect owner; Pinia does not own editable source, revisions, persistence, Drive sessions, audio, PWA lifecycle, or commands. Router and SSR remain unnecessary. The store does not claim runtime immutability: direct state assignment, `$patch()`, `$reset()`, and DevTools state edits are not supported application update paths.
- **CodeMirror 6:** accepted for the Web editor in Issue #172. Its transaction/history model supplies tab-local undo, editing commands, search, completion, lint and keyboard behavior while the existing document buffer and revision checks remain authoritative. It is not introduced into the VS Code TextEditor.
- **Custom `contenteditable` or a second textarea/highlight overlay:** rejected because it would duplicate native editing, selection, IME, history, and accessibility behavior that the established editor extension already provides.
- **A second compiler, score model, play-order engine, or renderer:** rejected because it would allow the VS Code and Web products to interpret the same source differently.
- **OAuth refresh-token persistence or full Drive scope:** rejected. The browser token model keeps tokens short-lived; `drive.file` covers user-authorized score files and `drive.appdata` covers only GuitarDSL application state.
- A flat Drive list, folder Picker as a destination, or automatic import of a selected folder: rejected because folder selection does not authorize its children under drive.file, and such UI would imply broader access than the app has.
- Folder move or trash, recursive full-Drive enumeration, or a virtual library tree: rejected. The library is a visible physical root and only its direct, authorized children are loaded as the user expands folders.
- **Automatic bidirectional sync or implicit move:** rejected. Local and Drive identities are distinct; Drive writes and local-to-Drive moves are explicit. Drive preflight detects known version changes, while the accepted GET→PATCH race remains possible across devices.
- **A Node-only shared PDF implementation in browser code:** rejected. The common API exchanges byte arrays and SVG page inputs, while host bundling is verified independently.

The Web SPA remains a browser-only static Vite artifact (`web/dist/`), without a Worker request handler, application backend, SSR, or Cloudflare Pages. The VS Code extension packaging/release, host adapter, shared core/score/PDF packages, IndexedDB, and Google Drive browser access are unchanged.

A second `guitardsl-dev` Worker is deliberately not created.

**Release gate:** `.github/workflows/cloudflare-workers.yml` is the sole automated deploy owner. The development job runs `wrangler preview --name dev` on `main`; the production job runs `wrangler deploy` only for tags whose checked-out commit is reachable from freshly fetched `origin/main`. Full history and ancestry validation include annotated/lightweight tags, fail before upload for off-main tags, and allow intentional releases of older ancestor commits. PRs do not deploy; obsolete development jobs may cancel; production releases may not.

**Build and security:** both jobs use Node 22, root lockfile `npm ci`, `npm run build:web` and `web/dist/index.html` validation. Wrangler 4.160.0 or newer supports Workers Previews. GitHub `development` and `production` environments isolate the optional public Vite build inputs (`VITE_GOOGLE_CLIENT_ID`, `VITE_GOOGLE_API_KEY`, `VITE_GOOGLE_APP_ID`); no client secrets or access tokens are compiled or uploaded. Cloudflare deployment token requires account Workers Edit and zone Workers Routes Write when domain configuration is managed.

**Operational invariants:** existing production Worker version is not overwritten while configuring Preview. The custom domain `guitardsl.app` stays routable for production. The `dev.guitardsl.app` hostname must not have conflicting Pages DNS or an older explicitly bound Worker domain; Cloudflare Preview routing handles its alias using the apex domain configuration and wildcard DNS/certificate. Experimental Pages projects may be removed only after confirming no deployments/data. Unrelated email MX/TXT records are preserved. Actual Preview deployment and browser OAuth/domain smoke tests are required before declaring success. Workers Builds/Git-connected auto deploy is not used.

### Independent product introduction Workers

Issue #188 adds a separate static product introduction without changing ownership or routing of the app Worker above. Japanese and English source pages live at `marketing/src/index.html` and `marketing/src/en/index.html`; original validated score fixtures live under `marketing/examples/`, and genuine Web app captures are distributed from `marketing/public/images/`. `scripts/build-marketing.mjs` builds the same source for one explicit `development` or `production` target into a clean `marketing/dist`. Its only environment substitutions are the literal app and site origins for that target. The marketing pages contain no runtime hostname detection, app state, first-run behavior, application backend, OAuth, analytics, external fonts, or service worker.

The production site is deployed from `marketing/dist` by Worker `guitardsl-marketing` on custom domain `www.guitardsl.app`. The development site uses independent Worker `guitardsl-marketing-dev` on `wwwdev.guitardsl.app`; it is not an app Preview alias. Both Worker configurations serve static assets without SPA fallback, keeping legal routes on the existing app domain and unknown marketing paths as 404 responses. The app's Product introduction Help action selects the corresponding marketing origin from the app build target and opens it safely in a new tab; the editor Help document, Welcome, Tutorial, and version/About remain distinct.

`.github/workflows/cloudflare-workers.yml` remains the sole deployment workflow. Existing `main` and tag-on-main gates, ancestry validation, environments, secrets, and concurrency remain in force. Each eligible environment builds and validates both the app and marketing outputs before either upload. A PR only builds/checks and never deploys. App and marketing uploads are sequential rather than atomic; if the second upload fails after the first succeeds, the workflow fails and status must report the partial deployment. After deployment, a release readback checks Cloudflare `Always Use HTTPS=on` and SSL `Full`, same-host HTTP-to-HTTPS redirect and TLS-valid HTTPS responses, each environment's app/site link target, 200 home responses, and marketing 404 behavior. Development checks the dev pair; production checks all four public hosts. The deployment token therefore needs Zone Read and Zone Settings Read in addition to its existing Worker deployment permissions. Local/CI verification includes both fixed-target builds, the parser-validated original examples, generated-page checks, and Chromium/WebKit browser checks against the built directories.
